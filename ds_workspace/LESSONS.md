# 从失败中学习：本工作区的工作规则

用户的原则：**从失败中学习**。本文把它变成可检查的条目——每一条都来自一份**已发生的失败**，
带出处，并且写明它在**下一次实验里具体禁止什么**。没有出处的条目不许写进这里。

出处标记：`[T]` = codex transcript 挖掘（`codex_failures_20260910/`）；`[R]` = 仓库侦察
（`recon_20260910/`）；`[O]` = 本次会话自己犯的错（最新，最该记住）。

## L1 局部量 ⇒ 能力 的跳接，是**重复了 10 次**的失败模式 `[T]`

codex 自己在 L47 读到的历史账本里，同一种错误有 10 行：早期 shape/theta（sigmoid 短/长
PPL 37648/62474 被判"更稳定、PASSED"）、Phase16 99 次运行（公式只赢 3/9 配置）、Phase18–23
（τ=1 时最高频仍是 ≈.72967 rad/token）、QuALITY、YaRN sqrt-gain 标错、Qwen 步长 16 混叠、
静态几何、Native compact、adaptation rank≈2000 全错、oracle routing。

**而且它在四小时内又被犯了两次**：Gap-capped 送 GPU、mean-protection 算子被构建。

> 根因（agent 自己在 L202 写的）：「**不是缺少又一个频率函数**……已有证据反复否定的是从某个
> **局部量**到**实际能力**的跳接；后续却把该局部量改名、增加自由度，或把错误前提重新当起点。」

**禁止**：任何候选，若其唯一理由是某个几何量的改善，直接淘汰。**我本次犯过**`[O]`：用
Phase 0 梯度算的 KKT 价格结构预测"EVQ 应该更好"（一阶预测 −10.41），而 EVQ 实测**劣于**
几何族——我用自己算的数验证了这条规则一次。**价格结构今后只作诊断量，不作能力声明。**

## L2 三个几何旋钮已被**证明**耗尽 `[T]`

固定 N、Σε=1、ε₀=ε_{N+1}=0 时，若 m_q ≤ m_Mr,q 对所有 q 且最大增量 ≤ c=2/(N+1)，
则 ε_N = c 被强制，R ≥ c²+c²/N = R_Mr，等号只在 ε 线性（= MrPro）处成立。
**精确 Fraction 算术验证 N=2..100。**

**禁止**：再把"原生位移 / 最大 gap / 粗糙度"三者组合成候选。**注意边界**：只覆盖
"处处不比 MrPro 更压缩"的表；b>1（后端更平）**不在**其内，所以 b 扫描未被它排除。

## L6 仪器口径必须与归档逐项对齐，否则差异归不到表上 `[O]`

**我本次犯过两次**：

1. 归档用 `pad_token_id = 100277`，我一开始写 `eos_token_id = 100257`——**不是 eos**。
   pad id 改变 padding mask，进而改变注意力与位置。分数照样出，但**与端点不可比**。
2. 归档是逐行前向，我按长度批 8–32 篇；bf16 归约非批不变，重测 MrPro 与归档差 **2.5e−4**，

混用两者 = 把 harness 差异记账到表上。

## L6b 「原生」参照必须点名 gain `[O]`

**我第三次犯同类错**：驱动的 `tbl()` 给**所有**臂装了 `gain = 1.1386`（YaRN 的 gain），
于是那条叫 `native` 的臂其实是"**原生频率 + YaRN gain**"，不是 checkpoint 自己的配置。
归档的 `Native` 用 `gain = 1.0`，两者在 32K 上差 **0.050 nats**——而我要测的效应是 1e−3 量级。

**它同时是一条真结果**（32K，同一批文档）：

| | NLL |
|---|---|
| 归档 Native（gain 1.0） | 2.03850 |
| 本run「native」= 原生频率 + YaRN gain | 2.08866 |
| MrPro（两种量法一致） | 2.08939 |

$$2.08939-2.03850 = \underbrace{0.0502}_{\text{gain}} + \underbrace{0.0007}_{\text{频率分配}}$$

> **MrRoPE 被归功的"窗内保护"，其窗内代价几乎全部来自它继承的 YaRN gain；它自己那张频率表
> 只花 0.0007 nats。**

**规则**：报"距原生多远"时必须同时说 **gain 是多少**。频率与 gain 是两个设计面
（INTEGRATION R3），混在一起报会把 gain 的账记到频率头上——反之亦然。已加
`native_gain1` 臂把这一分量直接测出来。

## L7 表非单调 ⇒ 槽位静默重排 `[O]`

规划 §2 **明文禁止**强制 m 单调（"会排除 EVQ 中的加速或非单调搬运"），而我的守卫一开始

## L8 退化的构造会浪费一次判决 `[O]`

规划字面写的 K6 四格（`max/min`）与 MrPro 只在**槽 38、39** 上不同——因为两条 m 曲线在
37/38 交叉，逐槽取较大频率几乎恒选 MrPro。**它不是"A 前段 + B 后段"，是只改最后两槽。**

**规则**：任何"反事实拼接"在送 GPU 前必须**先算它与原表差在几个槽上**。差 ≤2 槽的构造
测不出它声称要测的东西。

## L9 锚点要可机器检查，且**先说断言的精度** `[O]`

- `incr_r1` 与 `mrpro_n17` 是同一张表，必须**逐位**同分——回执里是硬门，不同则整张排行榜作废。
- `b=0` 对 MrPro 是**浮点**相等（2.8e−17，两次运算顺序不同），**不是逐位**；一开始我写成
  "逐位"，是错的。
- `b=1` 的参照一开始是我手打的 5 位小数，报出 2.2e−4 的假误差；换成精确有理数 `k(18−k)/969`
  后是 5.6e−17。

**规则**：断言写清是**逐位**还是**浮点容差**，参照量用**精确式**而非手抄小数。

## L10 调用方与被调方的**字典契约**没人钉住 ⇒ 链在第 2 段猝死 `[O]`

`anchor_check()` 返回 `incr_r1_bit_exact_vs_mrpro` 等新键，而 `kkt_residual.py`、

**规则**：任何跨文件的函数返回字典，必须有一个 `*_contract_keys()` 把键名钉住，
并在 selftest 里断言。已加 `anchor_contract_keys()`。

## L11 `pkill -f` / `pgrep -f` **匹配到自己的命令行** —— 本次犯了 **3 次** `[O]`

1. `pkill -f chain2.sh` —— 我的 ssh 命令串里就写着 `chain2.sh`，**杀掉自己的 shell**。
2. `pkill -f "tail -f -n 0 chain"` —— 同上，命令串里含这段字面量。
3. **更隐蔽的一种**：`chain_qwen_turns.sh` 里 `while pgrep -f chain_olmo; do sleep 30; done`，
   而**另一个 watcher 进程**的 `tail -f ... chain_olmo.log` 命令行里含 `chain_olmo`
   —— 等待条件永远为真，链永远不前进。**日志文件名会喂饱等待循环。**

**规则**：`pkill/pgrep -f` 的模式一律写成 `chai[n]` 这种**方括号断开**形式，
且不要用会被日志文件名命中的模式。等待别的 stage 时等**退出码**或**哨兵文件**，
不要等进程名。

## L12 链脚本 `echo "=== DONE ==="` 不看 `$?` ⇒ 失败被自己藏起来 `[O]`

旧的 `chain.sh` 每段后面无条件 echo 成功，于是日志里是
「round 1 finished → KKT done → ALL DONE」，三段间隔**1 秒**，
GPU 全程 0%。**日志显示全部成功，实际一步没跑。**

**规则**：每段包一个看 `$?` 的函数，失败时把 `tail -25` 打进主日志。
已在 `chain_v2.sh` 的 `run()` 里落实。
